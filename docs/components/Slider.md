# Slider

states: rest hover(thumb grows space1 per side, in pixels -- a percentage is under 1px on a small thumb) press(the growth is KEPT, the shadow lift doubles; a shrink contradicted the lift) focus(keyboard ring) disabled(every painted role through Style.disabled, colour never opacity, and still reads)
actions: Increase Decrease Minimum Maximum
size: sm|md|lg presets -- sm space1/iconSm, md space2/iconLg, lg space2/controlHeightSm -- and they are only the DEFAULT: thickness/thumbSize stay the primary API and survive a later size change. Main axis sliderLength / sliderLengthVertical, a constant, of which space1 at each end is reserved for the thumb's hover growth (so the track is two space1 steps shorter and the slots sit inside that reserve, keeping their gap at slotGap); cross axis at least controlHeightSm, at least the thumb plus space1 on both sides, and on a HORIZONTAL slider plus sliderThumbLift * 4 for the shadow -- a vertical one reserves that drop in its bottom padding instead, because the shadow drops along y in both orientations
tokens: sliderStep (the unit every non-pointer route walks in) sliderKeyboardUnits sliderPageUnits sliderLength sliderLengthVertical sliderThumbLift space1 (hover growth, sm track) space2 (slot gap, md/lg track) iconSm iconLg controlHeightSm accent surfaceHover text Style.disabled(opacityDisabled)
motion: fast+standardEasing on the painted position, and ONLY when the change did not come from a gesture; micro on the thumb growth and on the thumb colour; press on the shadow lift. Reduced motion REMOVES the position animation rather than shortening it, which overrides the library rule in Motion.qml -- a slider's job is to sit where it was put -- and shortens the growth and the lift the ordinary way
not designed: ticks, a value tooltip, a range (see the RangeSlider contract in the research), relative drag (Qt's press jumps absolutely, on PRESS)
notes: `committedValue` is the value the last GESTURE left behind -- written on every `committed()` emission and set to `value` at completion, never bound to it, so a host-driven write moves `value` while `committedValue` stays where the last gesture put it, and a host that only acts on a finished gesture compares against it instead of keeping its own copy; Accessible.role reads 0 offscreen because QQuickControl sets the attached role only while an accessibility bridge is active; role Slider is asserted by QQuickSlider::accessibleRole() in C++ and the value interface duck-types value/from/to/stepSize off the root
conflicts: none
known: `visualPosition` is recomputed from the orientation on every read but emits NO change signal when the orientation or the mirroring flips, so `_paintedPosition` names both as dependencies -- without them a slider flipped to vertical at runtime (which every preview unit is, because the host writes `variant` through `onLoaded`) went on painting the axis it was built with; the handle carries `z: 1` and the StateLayer follows it at `z: handle.z` -- QQuickSlider completes its handle BEFORE QQuickControl completes the contentItem, so the handle is the earlier sibling however the two are declared and the track and fill painted over the thumb; 1 is a stacking index rather than a measurement, so like `_wheelNotch` it stays a literal and is not a value a theme may retune; `pressed` is pointer-only here -- Qt's Slider also sets it from the arrows, and the dispatcher takes those before Qt sees them, so the thumb does not lift on a key press; `Keys.onReleased` accepts the release of exactly the keys the press dispatcher took, so only those are kept from QQuickSlider::keyReleaseEvent and every other key's release still reaches it; hoverEnabled follows enabled, because a HoverHandler forces acceptHoverEvents and hoverEnterEvent then sets hovered from hoverEnabled (re-enabling under a resting pointer restores hovered with no pointer move, measured); the horizontal wheel negates angleDelta.x, because Qt reports positive x when the top of the wheel goes left, and event.inverted is not consulted, so a natural-scrolling platform reads reversed; _wheelNotch 120 is a literal in the component and stays one -- it is the platform's wheel unit (eighths of a degree, 15 degrees per notch), not a design value a theme may retune; the a11y increase/decrease route writes value without emitting moved() or committed(), so a host wired only to onMoved never hears a screen-reader change and `committedValue` does not move for one either; one arrow press emits valueChanged once per unit (five times) and moved() once; a host that widens from/to must widen stepSize with it, because Home and End walk the range in units, and only a stepSize whose multiples can express the bound reaches it exactly (setValue refuses a write qFuzzyCompare-equal to the value it holds, so 0.1 saturates at 0.9999999999999999 while 0.01 lands on 1); arrows are on-axis only, and Page/Home/End are ours, not Qt parity; the wheel is taken by a MouseArea with acceptedButtons NoButton rather than by a WheelHandler, because a WheelHandler never receives a wheel event in a live Wayland window on this Qt6 QPA (measured against a MouseArea in the same scene) while both work offscreen, so the route passed its tests and was dead under a hand
